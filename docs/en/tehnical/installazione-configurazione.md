# Installation and configuration

[Italiano](../../tehnical/installazione-configurazione.md) | **English**

Guide checked against the repository files on **11 October 2026**. Commands assume the project root directory. [Architecture](architettura.md) and [network and security](rete-sicurezza.md) describe what starts; the [main README](../../../README.md) provides the quick entry point.

## Requirements

Docker requires Docker Engine **28 or later**, Docker Compose **2.36.0 or later**, Python 3 and OpenSSL. Networks require the `isolated` bridge gateway, `gw_priority` and `interface_name`. On macOS the daemon is the Linux daemon in Docker Desktop. Cluster scripts normally select the `desktop-linux` context on macOS; they accept `--docker-context` to change it.

Persistent space is needed for three SQL copies, GridFS and addon stores, plus a backup destination. The subnets from `172.30.10.0/24` through `172.30.80.0/24` defined in Compose must be available. Changing them requires aligning Compose, listeners, allowlists, checks and certificate SANs; changing a single subnet is not enough.

Default host ports are 80 and 443 for the app through NPM and `127.0.0.1:81` for administration. No database service or addon publishes a host port.

## First Docker installation

1. Copy the template without replacing an existing file:

   ```sh
   cp .env.docker.example .env.docker
   chmod 600 .env.docker
   ```

2. Fill in `PUNTO_EMAIL`, `PUNTO_PASSWORD`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `NPM_ADMIN_EMAIL` and `NPM_ADMIN_PASSWORD` in the actual file. Use distinct credentials. Configure `PUBLIC_ORIGINS` with the app's actual origins.
3. Leave `CLUSTER_REPLICATION_PASSWORD`, `CLUSTER_MONITOR_PASSWORD`, `DOC_DB_PASSWORD` and `DOC_DB_ROOT_PASSWORD` blank if you want initial generation. `init` generates distinct internal values and saves them in the file. The MySQL recovery channel password cannot exceed 32 bytes.
4. Prepare materials and initialize:

   ```sh
   python3 scripts/configure_network.py --env-file .env.docker prepare
   python3 scripts/manage_cluster.py --env-file .env.docker init
   python3 scripts/manage_cluster.py --env-file .env.docker status
   docker compose --env-file .env.docker ps
   ```

5. Configure NPM forwarding:

   ```sh
   python3 scripts/configure_proxy.py --env-file .env.docker
   ```

6. Check the public response and open the app:

   ```sh
   curl --fail http://localhost/healthz
   ```

`prepare` creates or checks certificates and secrets; it does not start the stack. `init` stops the app, preserves the first database, prepares the new empty members, creates the group and starts dependencies through Compose. It keeps markers in `data/cluster-state.json`. If the cluster is already marked as initialized, it invokes recovery without repeating the seed.

The procedure also supports the previous single-MySQL installation with an empty GTID history. It rejects seeding if the source already has GTIDs or a new node contains data unrelated to the expected preparation. In that case a clone or seed with the correct checkpoint must be designed, without removing the script's checks.

The first manager is created in a database with no users. Subsequently changing `PUNTO_EMAIL` or `PUNTO_PASSWORD` does not change the existing account. Likewise, changing only the variables file does not rotate accounts already present in MySQL or MongoDB.

## Domain and public HTTPS

Non-secret example of authorized origins:

```dotenv
PUBLIC_ORIGINS=http://localhost,http://127.0.0.1,https://progetti.example.com
```

Use complete origins without paths, credentials, wildcards or a trailing slash; include the port when it is not standard. At most 16 unique origins are allowed. After a change, recreate the app to reread its environment.

`configure_proxy.py` uses the local NPM API, initializes its administrator if the panel is new, and creates missing hosts forwarding to `http://app:8080`. It separates local and public names, checks existing hosts and stops on incompatible configurations. It does not request a public certificate or automatically enable HTTPS or forced redirects.

For the real domain, configure DNS and host reachability, then assign the certificate in the [local NPM](http://127.0.0.1:81) panel. Adjust the address if using a different administration port. Internal CA certificates generated by `prepare` serve databases and addons; they do not replace the domain's public certificate.

## Docker variables

The complete template is [.env.docker.example](../../../.env.docker.example). Real credentials must remain in the local file or dedicated secret files, without appearing in documentation, shell history, tickets or Git. Avoid publishing the complete output of `docker compose config`: it contains resolved values and passwords.

### Application and ingress

| Editable variable | Meaning and non-secret example value |
| --- | --- |
| `PUNTO_IMAGE_TAG` | Shared tag for local project images; `local` if absent or empty |
| `PUNTO_EMAIL` | First manager's email, for example `admin@example.test` |
| `PUNTO_PASSWORD` | Initial manager password; 8–1024 UTF-8 bytes, required in Compose |
| `PUBLIC_ORIGINS` | Origins accepted by the Host/Origin check |
| `NPM_HTTP_PORT` / `NPM_HTTPS_PORT` | Host ports, `80` / `443` |
| `NPM_ADMIN_PORT` | Local host port, `81` |
| `NPM_TZ` | NPM time zone, template default `Australia/Brisbane` |
| `NPM_ADMIN_EMAIL` / `NPM_ADMIN_PASSWORD` | Credentials read by the proxy script; password 8–64 characters |

Compose fixes `PORT=8080`, `BIND_HOST=172.30.20.10`, `PUBLIC_DIR=/app/public` and `TZ=Europe/Rome` for the app. `PUBLIC_PORT` derives from `NPM_HTTP_PORT`. Copying the native `.env.example` file does not configure the container environment.

### SQL and documents

| Variable | Purpose |
| --- | --- |
| `MYSQL_DATABASE` | Application database, default `punto` |
| `MYSQL_USER` / `MYSQL_PASSWORD` | SQL application account and password |
| `MYSQL_ROOT_PASSWORD` | SQL administration account, not provided to the app |
| `CLUSTER_REPLICATION_PASSWORD` | `punto_recovery` account, maximum 32 bytes |
| `CLUSTER_MONITOR_PASSWORD` | `punto_monitor` account for group status |
| `DOC_DB_NAME` / `DOC_DB_USER` | Document database and account, both default to `punto_documents` |
| `DOC_DB_PASSWORD` / `DOC_DB_ROOT_PASSWORD` | Distinct application and administration document passwords |

Compose translates SQL variables into `DB_HOST=db-proxy`, `DB_PORT=3306`, `DB_NAME`, `DB_USER` and `DB_PASSWORD`. It enforces `DB_TLS_MODE=verify_identity` and `DB_SSL_CA=/etc/punto/tls/ca.crt`. For MongoDB it sets host `documents`, port `27017` and `DOC_DB_SSL_CA` to the same CA. Do not remove identity verification to work around certificate errors.

### Email

| Variable | Purpose |
| --- | --- |
| `MAIL_SMTP_HOST` | Exact host; empty while SMTP remains deferred |
| `MAIL_SMTP_PORT` / `MAIL_SMTP_MODE` | `587` / `starttls`, or `465` / `smtps` |
| `MAIL_SMTP_FROM` | Sender authorized by the provider |
| `MAIL_SMTP_USER` | SMTP user if required |
| `MAIL_API_NAMESPACE` | Stable outbox key prefix, default `punto-alerts-v1` |

The SMTP password comes from `data/addon-secrets/smtp-password`, mounted as a secret. The private token is generated by `prepare` in `mail-api-token`. The app's internal connection is fixed at `https://mail-api:8090`, with a dedicated CA and token. The addon uses the `/var/lib/punto-mailer/delivery.sqlite3` ledger and a 20-second SMTP timeout.

Activation also requires the exact SMTP hostname in [allowed-smtp-domains.txt](../../../docker/squid/allowed-smtp-domains.txt). The current placeholder does not authorize a real provider. Check the outbox before activation: enabling SMTP may also make previously queued alerts eligible for delivery. The full procedure is in the [email manual](../../../addon/README.md).

### Calendar

| Variable | Purpose |
| --- | --- |
| `GOOGLE_CLIENT_ID` | Web OAuth client; empty until Google is configured |
| `GOOGLE_REDIRECT_URI` | Exact public URI, for example `https://progetti.example.com/api/calendar/oauth/callback` |
| `CALENDAR_SYNC_INTERVAL` | Polling, default `300` seconds |

The client secret is in `data/addon-secrets/google-client-secret`. `prepare` separately generates the `calendar-api-token` token and `calendar-token-key` AES key. The client secret file starts empty. The private service uses `https://calendar-api:8091`, the `/var/lib/punto-calendar/calendar.sqlite3` database, a 10-second Google timeout and a mandatory Squid proxy.

The Google ID, redirect and secret must be configured together; partial configurations are rejected. OAuth remains disabled until this configuration exists. Google accounts then require individual consent. The [Calendar manual](../../../calendar-addon/README.md) describes APIs, scopes, limits and activation. The connection GUI has not yet been implemented: the features exposed in this version are APIs.

## Updating existing services

Before updating, save a consistent backup as described in [operations](operazioni-backup-ripristino.md), retain credentials and check whether the new code contains migrations. The current schema is 10; starting an earlier version does not perform a reverse migration.

If the installation still uses the previous Compose names, first follow the [naming migration](nomi-servizi-e-immagini.md). New identities must not start alongside old containers using the same IPs and volumes.

For an application-only change:

```sh
docker compose --env-file .env.docker build app
docker compose --env-file .env.docker up -d --no-deps --force-recreate --wait app
```

To add or update integration services together on the current networks:

```sh
python3 scripts/configure_network.py --env-file .env.docker prepare
docker compose --env-file .env.docker build proxy-egress mail calendar inventory app proxy-web
docker compose --env-file .env.docker up -d --no-deps --force-recreate --wait proxy-egress mail calendar inventory app proxy-web
```

Recreation temporarily interrupts connections; recreating the app invalidates in-memory sessions. `--no-deps` avoids implicitly recreating databases but assumes dependencies are already available. Rebuild and recreate only the services actually changed when the intervention is narrower.

To migrate an already initialized cluster to the intended network segmentation, the dedicated command is:

```sh
python3 scripts/configure_network.py --env-file .env.docker apply
```

`apply` checks the engine and overlaps with other Docker networks, stops app/NPM/HAProxy, saves SQL, recreates members and invokes `recover`. This is maintenance with downtime, unlike updating only the binary. Do not change subnets of existing Docker networks without also planning their recreation and all related references.

## Internal certificates and secrets

`prepare` creates a private RSA 3072/SHA-256 CA valid for ten years and service certificates valid for one year. Materials are in `data/network-tls`; the CA key is not mounted in containers. Local directories have `0700` permissions, the CA key `0600`, public certificates `0644` and mounted key files `0444` for the different service UIDs. Local protection also depends on the parent directory and host access.

For an existing bundle, `prepare` checks expiry, key/certificate matching, chain, hostnames and IPs. It adds only expected missing leaf certificates; it does not automatically renew existing ones. It stops if the bundle is incomplete, inconsistent or near expiry, without deleting it.

Renewal is manual: retain the original materials, sign new leaf certificates with the intended CA and the same required SANs, verify them, install them in a maintenance window and recreate affected services. Rotating a CA requires a coordinated trust transition for all clients. Deleting the directory to rerun `prepare` is not a renewal procedure.

The `calendar-token-key` key decrypts the database already written. It cannot be replaced like a normal API token: rotation requires an explicit migration, which is not currently automated. The same volume will not open with a different key. See [security](rete-sicurezza.md) and [backup](operazioni-backup-ripristino.md).

## Native mode for development

A C11 compiler, make, Python 3 for tests, `pkg-config`, SQLite, libcurl, json-c and OpenSSL 3 are required (including on macOS, for OIDC verification). Password derivation uses Security/CommonCrypto on macOS and OpenSSL on Linux. Addons also require OpenSSL; Calendar requires pthread. The optional [Keycloak](keycloak.md) integration uses a shared realm for Punto and Ticket, with separate clients and user links.

```sh
make
make run
```

The server does not automatically load `.env` or `.env.example`: export the desired variables before startup. Explicitly set dedicated development credentials because the source contains a demo fallback for local startup. Example credentials must not be used for a shared deployment.

| Native variable | Default / behavior |
| --- | --- |
| `PORT` | `8080`, range 1024–65535 |
| `PUBLIC_PORT` | Same as `PORT`, range 1–65535 |
| `BIND_HOST` | `127.0.0.1`, IPv4 address |
| `PUBLIC_DIR` | `public` |
| `DB_PATH` | `data/punto.db`, used by the SQLite backend |
| `DOC_FILES_DIR` | `documents` directory next to the SQL file |
| `TZ` | `Europe/Rome` if not already defined |
| `PUBLIC_ORIGINS` | Additional authorized origins |

All three parameters `CALENDAR_API_URL`, `CALENDAR_API_TOKEN_FILE`, `CALENDAR_API_CA_FILE` must be present to connect the Calendar addon. Email uses `MAIL_API_URL`, `MAIL_API_TOKEN_FILE`, `MAIL_API_CA_FILE` and the namespace. Do not use an incomplete configuration. The container does not publish private APIs for native use: a dedicated development environment is required, without opening production ports as a shortcut.
